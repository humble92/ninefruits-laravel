- 작성일: 2026-10-22
- 대상: 개발팀, 프로젝트 관리자
- 관련: [이식 계획 14절 Phase 3](porting-plan.md#phase-3-입학-지원-최소-기능-m-신규), [설계 결정 0008](decisions/0008-admissions.md)

## 1. 요약

지원자 가입(이메일 인증), 모집 회차(상시 접수 포함), 지원서와 서류 업로드, 검토·결정·결과 발표, 합격자 등록 의사, 학생 전환(`MatriculateApplicant`)을 구현했다. 레거시에 없는 신규 기능이다.

- 테스트 287개(단언 962개) 통과. Phase 2 대비 28개 추가. Larastan 레벨 6 오류 0, Pint 위반 0, 명명 검사 위반 0, 번역 누락 0, `composer audit` 통과
- 빈 DB에서 `setup:install --force --profile=korean-university`, `setup:demo --size=small --seed=42` 성공. 데모 데이터에 `admission:matriculate`를 실제 실행해 등록 확정자 4명의 학적 생성 확인
- CI 결과는 7절

| 완료 기준 | 결과 | 근거 |
|---|---|---|
| 지원부터 첫 수강신청까지 같은 계정으로 끊김 없이 진행 | 충족 | `AdmissionJourneyTest`: 가입 → 이메일 확인 → 지원서 작성·서류 업로드·제출(수험 번호, 접수 메일) → 합격(발표 전에는 지원자에게 검토 중) → 결과 발표(메일, 응답 기한) → 등록 확정 → 학적 생성(새 학번, 입학 학기, 업무 감사) → 같은 계정이 학생 persona로 바뀌고, 같은 이메일과 비밀번호로 로그인해 내 학적 확인 → 신입생 대상 수강신청 기간에 `TermResolver`가 그 학기를 반환. 수강신청 자체는 Phase 5 |
| 재입학 시 이전 학적 보존 | 충족 | `AdmissionJourneyTest`: 졸업생이 기존 계정으로 지원해 학적 생성 → 학적 2개(이전 학적은 졸업 상태 그대로), 계정 1개. 신원 정보는 학적 담당 값 유지 |

## 3. 구현 내용

| 영역 | 테이블 | 화면 | 비고 |
|---|---|---|---|
| 가입 | `users`, `people` | 모집 안내(`/admissions`, 로그인 없이), 계정 만들기, 이메일 확인 | Fortify registration, email verification. 설정으로 끌 수 있음 |
| 모집 회차 | `admission_cycles`, `admission_cycle_programs`, `admission_cycle_document_types` | 입학 > 모집 회차(프로그램, 서류 포함), 회차별 결과 발표 | 상시 접수, 공개 여부, 결정 즉시 발표, 응답 기한 |
| 지원서 | `applications`, `application_number_sequences`, 미디어 | 포털 입학 지원(목록, 작성, 서류, 제출, 결과, 등록 의사, 포기), 입학 > 지원서(조회, 검토, 결정, 발표, 대리 응답, 학적 생성, 일괄 발표와 학적 생성) | 회차당 진행 중 지원 1건, 결정과 발표 분리 |
| 학생 전환 | `applications.student_record_id` | 지원서 화면의 학적 생성 | Phase 2 `RegisterStudent` 재사용 |
| 권한 | 권한 4개 | 설정 > 입학 | 입학 담당, 학적 담당, 학과 조교 역할 템플릿에 반영 |
| RLS | applications 정책, 지원자 인물 조회 정책 | — | 지원자는 SQL로도 합격 처리 불가 |

## 5. 발견해 고친 문제

- **작성 중 지원서 포기 불가**: 처음 작성한 CHECK 제약이 "작성 중, 만료가 아니면 수험 번호 필수"여서 제출 전 포기가 DB에서 거부되었다. 번호와 제출 시각의 일치, 제출 후 상태의 번호 필수로 나눠 해결.
- **검토 권한만 있는 담당자가 DB에서 지원서를 못 봄**: 수정 정책은 있는데 조회 정책이 `applications.view`만 보고 있었다. 애플리케이션 범위(조회 + 검토 병합)와 같도록 조회 정책에 검토 권한 추가. `ApplicationAccessTest`가 두 계층 결과를 비교한다.
- **Phase 2 설정 클래스 미등록**: 로그인 수단, 학적 설정이 `config/settings.php`에 등록되지 않아 설정 캐시에서 빠져 있었다(요청 시 해석되어 동작은 함). 입학 설정과 함께 등록.
- **올린 파일 형식 오류가 서버 오류로 표시**: 허용하지 않는 형식이 미디어 라이브러리 예외로 끝났다. 검증 메시지로 바꿈.

## 6. 실행 방법

`./vendor/bin/sail artisan setup:demo --size=small` 후 데모 계정(비밀번호 `demo-password`):

| 계정 | 내용 |
|---|---|
| `applicant@demo.test` | 제출한 지원서, 결과 대기 |
| `admitted@demo.test` | 합격 발표됨. 포털에서 등록 의사 응답 가능 |
| `admissions-officer@demo.test` | 입학 담당. 관리 화면 입학 메뉴 |

새 지원자 흐름은 `/admissions`에서 계정을 만들어 시험한다(메일은 Mailpit `http://localhost:8025`).
