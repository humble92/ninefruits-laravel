# Ачааллын тест (хичээл сонголтын оргил үе)

Хичээл сонголтын эхний өглөө шиг олон оюутан нэг зэрэг ижил бүлгүүд рүү давхцан хандах нөхцөлийг k6-аар дахин бий болгоно. Скрипт нь `tests/load/registration.js`.

## Бэлтгэл

1. Их хэмжээний демо өгөгдөл үүсгэж, оюутны бүртгэлүүдийг холбоно (бүртгэлийн жагсаалтын CSV `storage/app/private/load-accounts.csv`-д бичигдэнэ).

   ```bash
   ./vendor/bin/sail artisan setup:demo --size=large --seed=42 --student-accounts
   ```

2. Хичээл сонголтын үйл ажиллагааны хугацаа нээлттэй байх ёстой (демо нь одоогийн улирлын хичээллэх хугацааны хичээл сонголтын хугацааг нээдэг).
3. Дарааллын worker (Horizon) болон Redis ажиллаж байх ёстой. Суудал нөөцлөх болон хүлээлгийн жагсаалтаас дэвшүүлэх нь дараалалаар явагдана.

## Ажиллуулах

```bash
docker run --rm -i --network ninefruits-laravel_sail -v "$PWD":/work -w /work grafana/k6 run \
    --vus 200 --duration 2m -e BASE_URL=http://laravel.test -e ACCOUNTS=/work/storage/app/private/load-accounts.csv tests/load/registration.js
```

- `--vus`-ийг 100-аас 200, 500 хүртэл нэмж, `http_req_duration`-ийн p95 болон алдааны хувийг ажиглана. Зорилт: хичээл сонголтын дэлгэц p95 < 800ms, хичээл сонголтын хүсэлт p95 < 1.5s, алдааны хувь < 1%.
- Серверийн талд мөн `pg_stat_activity` дахь хүлээж буй (lock) сессийн тоо, Horizon-ийн боловсруулалтын саатал, php-fpm worker-ийн дүүргэлтийг ажиглана.
- Sail дээр ажиллуулахдаа суурилагдсан серверийн worker-ийн тоог нэмнэ (`.env` дахь `PHP_CLI_SERVER_WORKERS`, анхдагч 4). Worker-ийн тоо нэвтрүүлэх чадварыг хязгаарладаг.

## Дизайны баталгаа

- Багтаамжийг DB-ийн мөрийн түгжээгээр (`SeatAllocator::lock`) хамгаалдаг тул олон зэрэгцээ хүсэлт ирсэн ч бүлэгт багтаамжаас илүү бүртгэх боломжгүй (`ConcurrentRegistrationTest`).
- Суудал нөөцлөх нь Redis эсвэл дараалалгүйгээр зөвхөн DB-ээр зөв ажилладаг боловч хүлээлгийн жагсаалтаас дэвшүүлэх болон мэдэгдлийг дараалал гүйцэтгэнэ.

## Octane-ийн тухай шийдвэр

Sail дээрх ганц php-fpm-д p95 зорилтоос давбал эхлээд php-fpm worker-ийн тоо болон PostgreSQL-ийн `max_connections` эсвэл PgBouncer-ийг тохируулна. Тэгээд ч хангалтгүй бол Laravel Octane (FrankenPHP эсвэл Swoole)-ийг авч үзнэ. Octane руу шилжихээс өмнө шалгах зүйлс: хүсэлт бүрд дахин тохируулах ёстой төлөв (`DatabaseSessionContext`-ийн сессийн хувьсагчид хүсэлтийн төгсгөлд `reset()`-ээр буцаагддаг тул Octane дээр ч аюулгүй), singleton-д үлдсэн хэрэглэгчийн өгөгдөл, статик кэш. Шийдвэрийг бодит ачааллын тоог харсны дараа 13-р үе шатны тайланд бичнэ.

## 2026-10-23-ны үр дүн

Хөгжүүлэлтийн Sail контейнер (суурилагдсан сервер, opcache-гүй), 100 VU нэг минут: 4 worker-тэй 24.7 req/s, 16 worker-тэй 34.5 req/s, HTTP алдаа 0, багтаамжаас илүү бүртгэл 0, PostgreSQL холболт 4. Хүсэлт тус бүрийн серверийн хугацаа хуудсанд ойролцоогоор 120 ms, хичээл сонголтод 190 ms; 100 VU үеийн хэдэн секундын хоцрогдол нь worker-ийн дараалал юм. Нэвтрүүлэх чадвар PHP worker-ийн тоотой хамт өсөж, өгөгдлийн сан хязгаартаа хол байгаа тул **Octane-ийг нэвтрүүлэхгүй**: php-fpm worker-ийн тоо болон аппликейшн серверийг хэвтээ чиглэлд өргөтгөх нь хангалттай. Ашиглалтад оруулахаас өмнө php-fpm + opcache бүхий staging орчинд 200 болон 500 VU-гээр дахин ажиллуулна. Бүрэн тоо: [13-р үе шатны тайлан](../../../../porting/phase-13-report.md)-ын 7-р хэсэг.
