# Аудитын бүрэн бүтэн байдал ба тогтмол засвар үйлчилгээ

## Аудитын хэш гинж

Аудитын хүснэгтүүд (өгөгдлийн өөрчлөлтийн `audit.record_changes`, бизнесийн үйлдлийн `audit.activity_log`, аюулгүй байдлын үйл явдлын `audit.security_events`) зөвхөн нэмэх боломжтой (trigger-ээр хангагдана). Үүн дээр нэмж хуурамчаар өөрчилсөн байдлыг **ил гаргах** механизм бий.

- Мөр бүрийг оруулах үед түүний агуулгын SHA-256 (`row_hash`) тооцогдоно.
- `audit:seal` (өдөр бүр 03:30-д төлөвлөгдсөн) шинэ мөрүүдийг ID-ийн дарааллаар гинжинд холбоно: `chain_hash = SHA-256(previous chain_hash || row_hash)`.
- `audit:verify-chain` мөр бүрийн агуулгын хэш болон гинжийг дахин тооцоолно. Агуулга нь өөрчлөгдсөн мөрийг "row mismatch", алга болсон эсвэл дараалал нь өөрчлөгдсөн мөрийг "chain mismatch" гэж мэдээлж, команд exit code 2 буцаана.

Анхаарах зүйлс

- Битүүмжлэгдэхээс өмнө (тухайн өдөртөө) өөрчлөгдсөн мөрийг гинж илрүүлж чадахгүй. Тиймээс битүүмжлэлийг өдөр бүр, шалгалтыг нөөцлөхийн өмнө болон аюулгүй байдлын хяналтын үеэр хийнэ.
- Цэвэрлэлт (`audit:prune`) хамгийн хуучин мөрүүдийг устгахад үлдсэн эхний мөрийн холбоосыг шалгахгүй (цэвэрлэсэн хүрээ нь цэвэрлэх командын аудитын бичлэгт хадгалагдана).
- Зөвхөн DB-ийн админ (схемийн эзэмшигч) `app.audit_maintenance = on` тохируулж чадна. Аппликейшны рольд UPDATE эсвэл DELETE эрх байхгүй.

## Хадгалах хугацаа ба цэвэрлэлт

1. Хадгалах хугацааг тогтооно (жишээ нь өгөгдлийн өөрчлөлт 3 жил, бизнесийн үйлдэл 5 жил, аюулгүй байдлын үйл явдал 1 жил).
2. Цэвэрлэхийн өмнө нөөцөлж ([Нөөцлөлт ба сэргээлт](backup-restore.md)), `audit:verify-chain`-ээр гинж бүрэн бүтэн эсэхийг шалгана.
3. `audit:prune --before=YYYY-MM-DD --table=record_changes --dry-run`-аар тоог шалгаад `--dry-run`-гүйгээр ажиллуулна. Битүүмжлэгдээгүй мөрүүд хэзээ ч устахгүй тул эхлээд `audit:seal` ажиллуулна.
4. Цэвэрлэсний дараа `audit:verify-chain`-ийг дахин ажиллуулна.

Цэвэрлэлт өөрөө бүртгэгддэг: ажиллах бүрд үйлдлийн бүртгэлд (log `command`) хязгаар огноо, сонголтууд, гүйцэтгэгч болон үйлдлийн системийн хэрэглэгч, мөн хүснэгт тус бүрээр **устгасан мөрийн тоо, устгасан ID-ийн хүрээ, хил дээрх chain_hash** бичигдэнэ; бодит устгалт мөн аюулгүй байдлын үйл явдал `audit.pruned` болж бүртгэгдэнэ (**Аудит > Аюулгүй байдлын үйл явдлууд**). Энэ бичлэгийн мөр өөрөө дараагийн битүүмжлэлээр гинжинд холбогдоно. Энэ хил нь яг `audit:verify-chain` үлдсэн эхний мөрийн холбоосыг шалгадаггүй шалтгаан юм; хилийн хэшийг цэвэрлэлтийн бичлэгтэй харьцуулснаар устгагдсан хүрээ нь бүртгэгдсэн цэвэрлэлттэй таарч байгааг баталж болно.

## Файл цэвэрлэх

`media:prune-orphans --dry-run` нь эзэмшигч нь байхаа больсон медиа мөрүүд болон мөргүй директоруудыг жагсаана; `--dry-run`-гүйгээр тэдгээрийг устгана. Хувь хүний зураг, өргөдлийн баримт, тодорхойлолтын PDF, шалгалтын нотлох баримтыг хамарна. Сар бүр эсвэл их хэмжээний устгалтын дараа ажиллуулна.

## Эрүүл мэндийн шалгалт

`system:health-check` нь тохиргоо ба түлхүүр, DB-ийн роль ба RLS, миграц, эрхийн каталог, Redis ба дараалал (Horizon), Gotenberg, хадгалалт болон төлөвлөгчийн heartbeat-ийг (минут тутам кэшид бичигддэг) шалгаж, ямар нэг асуудал байвал exit code 2 буцаана. Мониторингтой холбохдоо `--json` ашиглана.
