# लोड परीक्षण (विषय दर्ताको उच्च चाप)

विषय दर्ताको पहिलो बिहानजस्तै, धेरै विद्यार्थीहरू एकै पटक एउटै सेक्सनतर्फ दौडिने अवस्थालाई k6 मार्फत पुनरुत्पादन गर्छ। स्क्रिप्ट `tests/load/registration.js` हो।

## तयारी

1. ठूलो डेमो डेटा सेट बनाउनुहोस् र विद्यार्थी खाताहरू जोड्नुहोस् (खाता सूचीको CSV `storage/app/private/load-accounts.csv` मा लेखिन्छ)।

   ```bash
   ./vendor/bin/sail artisan setup:demo --size=large --seed=42 --student-accounts
   ```

2. विषय दर्ता कार्य अवधि खुला हुनुपर्छ (डेमोले हालको सेमेस्टरको सत्रको विषय दर्ता कार्य अवधि खोल्छ)।
3. क्यु वर्कर (Horizon) र Redis चलिरहेका हुनुपर्छ। सिट आरक्षण र प्रतीक्षा सूचीबाट बढुवा क्यु मार्फत चल्छन्।

## चलाउने

```bash
docker run --rm -i --network ninefruits-laravel_sail -v "$PWD":/work -w /work grafana/k6 run \
    --vus 200 --duration 2m -e BASE_URL=http://laravel.test -e ACCOUNTS=/work/storage/app/private/load-accounts.csv tests/load/registration.js
```

- `--vus` लाई 100 बाट 200, अनि 500 सम्म बढाउँदै `http_req_duration` को p95 र विफलता दर हेर्नुहोस्। लक्ष्यहरू: विषय दर्ता स्क्रिन p95 < 800ms, दर्ता अनुरोध p95 < 1.5s, विफलता दर < 1%।
- सर्भर पक्षमा, `pg_stat_activity` मा प्रतीक्षारत (लक) सत्रहरूको सङ्ख्या, Horizon प्रशोधन ढिलाइ र php-fpm वर्करको संतृप्ति पनि हेर्नुहोस्।
- Sail विरुद्ध चलाउँदा, बिल्ट-इन सर्भरको वर्कर सङ्ख्या बढाउनुहोस् (`.env` मा `PHP_CLI_SERVER_WORKERS`, पूर्वनिर्धारित 4)। वर्कर सङ्ख्याले थ्रुपुटको सीमा तोक्छ।

## डिजाइनले के ग्यारेन्टी गर्छ

- क्षमता DB पङ्क्ति लक (`SeatAllocator::lock`) ले सुरक्षित गरिएको छ, त्यसैले एकैसाथ आएका अनुरोधहरूको बाढीले पनि सेक्सनमा क्षमताभन्दा बढी दर्ता गराउन सक्दैन (`ConcurrentRegistrationTest`)।
- सिट आरक्षण Redis वा क्यु बिना DB मा मात्र पनि सही हुन्छ, तर प्रतीक्षा सूचीबाट बढुवा र सूचनाहरू क्युले सम्हाल्छ।

## Octane बारे निर्णय

Sail अन्तर्गत एकल php-fpm मा p95 लक्ष्यभन्दा बढी भएमा, पहिले php-fpm वर्करहरूको सङ्ख्या र PostgreSQL `max_connections` वा PgBouncer मिलाउनुहोस्। त्यति पनि पर्याप्त नभएमा Laravel Octane (FrankenPHP वा Swoole) विचार गर्नुहोस्। Octane मा सर्नुअघि जाँच गर्नुहोस्: प्रत्येक अनुरोधमा रिसेट गर्नुपर्ने अवस्था (`DatabaseSessionContext` का सत्र चरहरू अनुरोधको अन्त्यमा `reset()` ले फर्काइन्छन्, त्यसैले Octane अन्तर्गत पनि सुरक्षित छन्), सिङ्गलटनमा रहेको प्रयोगकर्ता डेटा, स्थिर क्यासहरू। वास्तविक लोडका तथ्याङ्क हेरेपछि यो निर्णय Phase 13 प्रतिवेदनमा लेखिन्छ।

## 2026-10-23 का नतिजाहरू

विकास Sail कन्टेनर (बिल्ट-इन सर्भर, opcache बिना), एक मिनेटका लागि 100 VU: 4 वर्करसँग 24.7 req/s, 16 वर्करसँग 34.5 req/s, 0 HTTP विफलता, क्षमताभन्दा बढी दर्ता 0, PostgreSQL जडान 4। प्रति अनुरोध सर्भर समय पृष्ठका लागि करिब 120 ms र दर्ताका लागि 190 ms; 100 VU मा देखिएको धेरै सेकेन्डको ढिलाइ वर्करको लाममा पर्खाइ हो। थ्रुपुट PHP वर्करको सङ्ख्यासँगै बढ्छ र डेटाबेस आफ्नो सीमाभन्दा धेरै टाढा छ, त्यसैले **Octane अपनाइँदैन**: php-fpm वर्कर सङ्ख्या र एप सर्भरहरूको तेर्सो विस्तार पर्याप्त छ। सञ्चालनमा जानुअघि php-fpm + opcache भएको स्टेजिङ वातावरणमा 200 र 500 VU सँग फेरि चलाउनुहोस्। पूर्ण तथ्याङ्क: [Phase 13 प्रतिवेदन](../../../../porting/phase-13-report.md) खण्ड 7।
