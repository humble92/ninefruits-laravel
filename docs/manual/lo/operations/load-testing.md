# ການທົດສອບພາລະ (ຊ່ວງສູງສຸດຂອງການລົງທະບຽນຮຽນ)

ຈຳລອງສະຖານະການທີ່ນັກສຶກສາຈຳນວນຫຼາຍແຫ່ເຂົ້າກຸ່ມຮຽນດຽວກັນພ້ອມກັນ ເຊັ່ນ ຕອນເຊົ້າຂອງມື້ທຳອິດຂອງການລົງທະບຽນຮຽນ ດ້ວຍ k6. ສະຄຣິບຢູ່ທີ່ `tests/load/registration.js`.

## ການກຽມ

1. ສ້າງຂໍ້ມູນເດໂມຂະໜາດໃຫຍ່ ແລະ ຕິດບັນຊີນັກສຶກສາ (ລາຍຊື່ບັນຊີ CSV ຈະຖືກສ້າງທີ່ `storage/app/private/load-accounts.csv`).

   ```bash
   ./vendor/bin/sail artisan setup:demo --size=large --seed=42 --student-accounts
   ```

2. ໄລຍະການລົງທະບຽນຮຽນຕ້ອງເປີດຢູ່ (ເດໂມຈະເປີດໄລຍະລົງທະບຽນຮຽນຂອງເຊສຊັນພາກຮຽນປັດຈຸບັນ).
3. ຕົວປະມວນຜົນຄິວ (Horizon) ແລະ Redis ຕ້ອງແລ່ນຢູ່. ການຈອງບ່ອນນັ່ງ ແລະ ການເລື່ອນຂຶ້ນຈາກລາຍຊື່ລໍຖ້າແລ່ນຜ່ານຄິວ.

## ການແລ່ນ

```bash
docker run --rm -i --network ninefruits-laravel_sail -v "$PWD":/work -w /work grafana/k6 run \
    --vus 200 --duration 2m -e BASE_URL=http://laravel.test -e ACCOUNTS=/work/storage/app/private/load-accounts.csv tests/load/registration.js
```

- ເພີ່ມ `--vus` ຈາກ 100 → 200 → 500 ແລະ ສັງເກດ p95 ຂອງ `http_req_duration` ແລະ ອັດຕາຄວາມລົ້ມເຫຼວ. ເກນ: ໜ້າລົງທະບຽນຮຽນ p95 < 800ms, ການລົງທະບຽນ p95 < 1.5s, ອັດຕາຄວາມລົ້ມເຫຼວ < 1%.
- ທາງຝັ່ງເຊີບເວີ ໃຫ້ສັງເກດຈຳນວນການລໍຖ້າ (lock) ໃນ `pg_stat_activity`, ຄວາມລ່າຊ້າໃນການປະມວນຜົນຂອງ Horizon ແລະ ການອີ່ມຕົວຂອງ worker php-fpm ພ້ອມກັນ.
- ເມື່ອແລ່ນກັບ Sail ໃຫ້ເພີ່ມຈຳນວນ worker ຂອງເຊີບເວີໃນຕັວ (`PHP_CLI_SERVER_WORKERS` ໃນ `.env`, ຄ່າເລີ່ມຕົ້ນ 4). ຈຳນວນ worker ແມ່ນຂີດຈຳກັດຂອງຜົນຜະລິດ.

## ສິ່ງທີ່ຮັບປະກັນໂດຍການອອກແບບ

- ຈຳນວນຮັບຖືກຮັກສາດ້ວຍການລັອກແຖວຂອງ DB (`SeatAllocator::lock`) ດັ່ງນັ້ນເຖິງວ່າຄຳຮ້ອງຂໍພ້ອມກັນຈະແຫ່ເຂົ້າມາ ກໍຈະບໍ່ມີການລົງທະບຽນເກີນຈຳນວນຮັບ (`RegistrationConcurrencyTest`).
- ການຈອງບ່ອນນັ່ງຖືກຕ້ອງໃນ DB ເຖິງວ່າຈະບໍ່ມີ Redis ຫຼື ຄິວ ແຕ່ການເລື່ອນຂຶ້ນຈາກລາຍຊື່ລໍຖ້າ ແລະ ການແຈ້ງເຕືອນຈະຖືກປະມວນຜົນໂດຍຄິວ.

## ການຕັດສິນໃຈກ່ຽວກັບ Octane

ຖ້າ p95 ເກີນເກນເມື່ອວັດດ້ວຍ php-fpm ດຽວຂອງ Sail ໃຫ້ປັບຈຳນວນ worker ຂອງ php-fpm ແລະ `max_connections` ຂອງ PostgreSQL ຫຼື PgBouncer ກ່ອນ. ຖ້າຍັງບໍ່ພໍ ໃຫ້ພິຈາລະນາ Laravel Octane (FrankenPHP ຫຼື Swoole). ສິ່ງທີ່ຕ້ອງກວດກ່ອນປ່ຽນໄປໃຊ້ Octane: ສະຖານະທີ່ຕ້ອງຖືກຕັ້ງຄ່າໃໝ່ທຸກຄຳຮ້ອງຂໍ (ຕົວແປເຊສຊັນຂອງ `DatabaseSessionContext` ຖືກຄືນຄ່າດ້ວຍ `reset()` ເມື່ອສິ້ນສຸດຄຳຮ້ອງຂໍ ຈຶ່ງປອດໄພໃນ Octane ເຊັ່ນກັນ), ຂໍ້ມູນຜູ້ໃຊ້ທີ່ຄ້າງຢູ່ໃນ singleton, static cache. ການຕັດສິນໃຈຈະຖືກບັນທຶກໃນບົດລາຍງານ Phase 13 ຫຼັງຈາກເຫັນຕົວເລກພາລະຕົວຈິງແລ້ວ.

## ຜົນການວັດແທກ 2026-10-23

ຄອນເທນເນີ Sail ສຳລັບການພັດທະນາ (ເຊີບເວີໃນຕັວ, ບໍ່ມີ opcache), 100 VU ເປັນເວລາ 1 ນາທີ: worker 4 ຕັວ 24.7 req/s, worker 16 ຕັວ 34.5 req/s, HTTP ລົ້ມເຫຼວ 0, ການລົງທະບຽນເກີນຈຳນວນ 0, ການເຊື່ອມຕໍ່ PostgreSQL 4 ຕັວ. ເວລາປະມວນຜົນຂອງເຊີບເວີຕໍ່ຄຳຮ້ອງຂໍແມ່ນປະມານ 120 ms ສຳລັບໜ້າຈໍ ແລະ 190 ms ສຳລັບການລົງທະບຽນ; ຄວາມຊັກຊ້າຫຼາຍວິນາທີທີ່ 100 VU ແມ່ນການລໍຖ້າຄິວຂອງ worker. ຜົນຜະລິດເພີ່ມຕາມຈຳນວນ worker ຂອງ PHP ແລະ ຖານຂໍ້ມູນຍັງຫ່າງຈາກຂີດຈຳກັດ ສະນັ້ນ **ບໍ່ນຳໃຊ້ Octane**: ຈຳນວນ worker ຂອງ php-fpm ແລະ ການຂະຫຍາຍເຊີບເວີແອັບຕາມແນວນອນກໍພຽງພໍ. ກ່ອນນຳໃຊ້ຈິງ ໃຫ້ແລ່ນຊ້ຳດ້ວຍ 200 ແລະ 500 VU ໃນສະພາບແວດລ້ອມທົດສອບທີ່ໃຊ້ php-fpm + opcache. ຕັວເລກລະອຽດ: [ບົດລາຍງານ Phase 13](../../../porting/phase-13-report.md) ພາກທີ 7.
