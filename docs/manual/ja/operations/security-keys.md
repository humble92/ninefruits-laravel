# キー管理

- 対象読者: IT 運用担当者

| キー | 用途 | 紛失した場合 | ローテーション |
|---|---|---|---|
| `APP_KEY` | セッション、Cookie、二要素認証のシークレット、記憶されたデバイスの Cookie の署名 | すべてのユーザーがログアウトされ、登録済みの二要素認証(認証アプリ)が機能しなくなります | 以前のキーを `APP_PREVIOUS_KEYS` に設定してからローテーションします |
| `PII_ENCRYPTION_KEY` | 国民識別番号などの個人情報の暗号化 | **暗号化された個人情報は復元できません** | 下記の手順 |
| `PII_HASH_KEY` | 個人情報の完全一致検索用のハッシュ | 検索が機能しなくなります(データは残ります) | 原則としてローテーションしません |

保管の原則

- 3 つのキーは、サーバーの環境設定とは別に、シークレットストア(Vault、クラウドのシークレットマネージャーなど)または封印したオフラインの保管場所に少なくとも 2 部保管します。
- バックアップファイルと一緒には決して保管しないでください。DB のバックアップが流出しても、キーがなければ個人情報が読めない状態を保つ必要があります。

## 個人情報キーのローテーション手順

1. `php artisan pii:generate-key` で新しいキーを生成します(出力のうち `PII_ENCRYPTION_KEY` のみを使用します)。
2. 現在のキーを `PII_PREVIOUS_KEYS`(複数ある場合はカンマ区切り)に、新しいキーを `PII_ENCRYPTION_KEY` に設定します。
3. 設定を再読み込みします: `php artisan config:cache`、`php artisan horizon:terminate`。
4. 個人情報のモデルごとに、`php artisan pii:reencrypt {model} --dry-run` で対象レコードの件数を確認してから、`--force` なしで実行します。
5. Horizon でバッチの完了が表示され、`--dry-run` が 0 を報告したら、`PII_PREVIOUS_KEYS` から以前のキーを削除します。
6. 以前のキーは、バックアップの保存期間中は封印して保管します(古いバックアップを復元するのに必要です)。
