# 監査の完全性と定期メンテナンス

## 監査ハッシュチェーン

監査テーブル(データ変更履歴の `audit.record_changes`、業務ログの `audit.activity_log`、セキュリティイベントの `audit.security_events`)は追記専用です(トリガーで強制)。そのうえで、改ざんを**明らかにする**仕組みがあります。

- すべての行は挿入時に内容の SHA-256(`row_hash`)を持ちます。
- `audit:seal`(毎日 03:30 にスケジュール実行)は、新しい行を ID 順にチェーンへ連結します: `chain_hash = SHA-256(直前の chain_hash || row_hash)`。
- `audit:verify-chain` は、すべての行について内容ハッシュとチェーンを再計算します。内容が変更された行は「row mismatch」、欠落した行や順序が入れ替わった行は「chain mismatch」として報告され、コマンドは終了コード 2 を返します。

留意点

- 封印される前(同じ日のうち)に変更された行は、チェーンでは検出できません。そのため封印は毎日行い、検証はバックアップ前とセキュリティレビュー時に行います。
- 削除(`audit:prune`)で最も古い行が削除されると、残った最初の行の連結はチェックされません(削除された範囲は削除コマンドの監査記録に保存されます)。
- `app.audit_maintenance = on` を設定できるのは DB 管理者(スキーマ所有者)だけです。アプリケーションのロールには UPDATE と DELETE の権限がありません。

## 保存期間と削除

1. 保存期間を決めます(例: データ変更履歴 3 年、業務ログ 5 年、セキュリティイベント 1 年)。
2. 削除の前にバックアップを取り([バックアップと復元](backup-restore.md))、`audit:verify-chain` でチェーンに問題がないことを確認します。
3. `audit:prune --before=YYYY-MM-DD --table=record_changes --dry-run` で件数を確認してから、`--dry-run` なしで実行します。封印されていない行は削除されないため、先に `audit:seal` を実行してください。
4. 削除後に再度 `audit:verify-chain` を実行します。

削除そのものも記録されます。実行のたびに、基準日、オプション、実行者、OS ユーザーに加えて、テーブルごとの**削除行数、削除された ID の範囲、境界の chain_hash** が業務ログ(ログ `command`)に書き込まれます。実際に削除した場合は、セキュリティイベント `audit.pruned` としても記録されます(**監査 > セキュリティイベント**)。この記録行自体も、次回の封印でチェーンに連結されます。この境界こそが、`audit:verify-chain` が残った最初の行の連結をチェックしない理由です。境界のハッシュを削除記録と照合すれば、削除された範囲が記録された削除と一致することを確認できます。

## ファイルのクリーンアップ

`media:prune-orphans --dry-run` は、所有者が存在しなくなったメディアの行と、行のないディレクトリを一覧表示します。`--dry-run` なしで実行すると、それらを削除します。対象は人物の写真、出願書類、証明書の PDF、試験の証拠資料です。毎月、または一括削除の後に実行します。

## ヘルスチェック

`system:health-check` は、設定とキー、DB ロールと RLS、マイグレーション、権限カタログ、Redis とキュー(Horizon)、Gotenberg、ストレージ、スケジューラーのハートビート(毎分キャッシュに書き込まれます)をチェックし、問題がある場合は終了コード 2 を返します。監視と連携するには `--json` を使用します。
