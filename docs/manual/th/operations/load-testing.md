# การทดสอบโหลด (ช่วงลงทะเบียนเรียนหนาแน่น)

จำลองด้วย k6 สถานการณ์ที่นักศึกษาจำนวนมากแย่งลงทะเบียนกลุ่มเรียนเดียวกันพร้อมกัน เช่นในเช้าวันแรกของการลงทะเบียนเรียน สคริปต์คือ `tests/load/registration.js`

## การเตรียมการ

1. สร้างชุดข้อมูลสาธิตขนาดใหญ่และสร้างบัญชีนักศึกษา (ไฟล์ CSV รายชื่อบัญชีจะถูกเขียนไปที่ `storage/app/private/load-accounts.csv`)

   ```bash
   ./vendor/bin/sail artisan setup:demo --size=large --seed=42 --student-accounts
   ```

2. ต้องมีช่วงเวลาลงทะเบียนเรียนที่เปิดอยู่ (ข้อมูลสาธิตจะเปิดช่วงเวลาลงทะเบียนเรียนของช่วงการเรียนในภาคการศึกษาปัจจุบัน)
3. ตัวประมวลผลคิว (Horizon) และ Redis ต้องทำงานอยู่ การจองที่นั่งและการเลื่อนรายชื่อสำรองทำงานผ่านคิว

## การรัน

```bash
docker run --rm -i --network ninefruits-laravel_sail -v "$PWD":/work -w /work grafana/k6 run \
    --vus 200 --duration 2m -e BASE_URL=http://laravel.test -e ACCOUNTS=/work/storage/app/private/load-accounts.csv tests/load/registration.js
```

- เพิ่ม `--vus` จาก 100 เป็น 200 และ 500 แล้วสังเกตค่า p95 ของ `http_req_duration` และอัตราความล้มเหลว เป้าหมาย: หน้าจอลงทะเบียนเรียน p95 < 800ms คำขอลงทะเบียน p95 < 1.5s อัตราความล้มเหลว < 1%
- ฝั่งเซิร์ฟเวอร์ ให้สังเกตจำนวนเซสชันที่รอ (lock) ใน `pg_stat_activity` ความล่าช้าในการประมวลผลของ Horizon และการใช้งานเวิร์กเกอร์ php-fpm จนเต็มด้วย
- เมื่อทดสอบกับ Sail ให้เพิ่มจำนวนเวิร์กเกอร์ของเซิร์ฟเวอร์ในตัว (`PHP_CLI_SERVER_WORKERS` ใน `.env` ค่าเริ่มต้น 4) จำนวนเวิร์กเกอร์เป็นตัวจำกัดปริมาณงานที่รองรับได้

## สิ่งที่การออกแบบรับประกัน

- ความจุได้รับการป้องกันด้วยการล็อกแถวในฐานข้อมูล (`SeatAllocator::lock`) แม้มีคำขอพร้อมกันจำนวนมาก กลุ่มเรียนก็จะไม่รับเกินความจุ (`ConcurrentRegistrationTest`)
- การจองที่นั่งถูกต้องด้วยฐานข้อมูลเพียงอย่างเดียว โดยไม่ต้องพึ่ง Redis หรือคิว แต่การเลื่อนรายชื่อสำรองและการแจ้งเตือนจัดการผ่านคิว

## การตัดสินใจเรื่อง Octane

หาก p95 เกินเป้าหมายบน php-fpm เครื่องเดียวภายใต้ Sail ให้ปรับจำนวนเวิร์กเกอร์ php-fpm และ `max_connections` ของ PostgreSQL หรือ PgBouncer ก่อน หากยังไม่เพียงพอ จึงพิจารณา Laravel Octane (FrankenPHP หรือ Swoole) ก่อนเปลี่ยนไปใช้ Octane ให้ตรวจสอบ: สถานะที่ต้องรีเซ็ตทุกคำขอ (ตัวแปรเซสชันของ `DatabaseSessionContext` จะถูกคืนค่าด้วย `reset()` เมื่อสิ้นสุดคำขอ จึงปลอดภัยภายใต้ Octane เช่นกัน) ข้อมูลผู้ใช้ที่ค้างอยู่ใน singleton และแคชแบบ static การตัดสินใจจะบันทึกไว้ในรายงาน Phase 13 หลังจากดูตัวเลขโหลดจริง

## ผลการทดสอบวันที่ 2026-10-23

คอนเทนเนอร์ Sail สำหรับพัฒนา (เซิร์ฟเวอร์ในตัว ไม่มี opcache) 100 VU เป็นเวลาหนึ่งนาที: 24.7 req/s ด้วย 4 เวิร์กเกอร์, 34.5 req/s ด้วย 16 เวิร์กเกอร์, ความล้มเหลว HTTP 0 รายการ, การรับเกินความจุ 0 รายการ, การเชื่อมต่อ PostgreSQL 4 รายการ เวลาประมวลผลฝั่งเซิร์ฟเวอร์ต่อคำขอประมาณ 120 ms สำหรับหน้าจอ และ 190 ms สำหรับการลงทะเบียน ความหน่วงหลายวินาทีที่ 100 VU เกิดจากการรอคิวของเวิร์กเกอร์ ปริมาณงานเพิ่มขึ้นตามจำนวนเวิร์กเกอร์ PHP และฐานข้อมูลยังห่างไกลจากขีดจำกัด จึง **ไม่นำ Octane มาใช้**: จำนวนเวิร์กเกอร์ php-fpm และการขยายเซิร์ฟเวอร์แอปพลิเคชันในแนวนอนก็เพียงพอ ให้ทดสอบซ้ำด้วย 200 และ 500 VU บนสภาพแวดล้อม staging ที่ใช้ php-fpm + opcache ก่อนเปิดใช้งานจริง ตัวเลขทั้งหมด: [รายงาน Phase 13](../../../../porting/phase-13-report.md) หัวข้อที่ 7
