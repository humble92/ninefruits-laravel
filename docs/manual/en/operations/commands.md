# Artisan command reference

- Audience: IT operators
- Scope: every application command registered in this repository. When a command is added it must also be added here, or CI fails (`tests/Feature/Tooling/CommandDocumentationTest.php`).

## Common conventions

Every command runs as `php artisan {command}`. In the development environment, `./vendor/bin/sail artisan {command}`.

| Item | Rule |
|---|---|
| Audit record | Commands that change data ("Audit: recorded" below) write the command, arguments, options, OS user, exit code and result to the activity log (log `command`) on every run. Check them under **Audit > Activity log** in the administration panel |
| Run ID | Every run gets an ID starting with `cmd-` in place of the request ID. The activity log, the data changes made by that run and the queue jobs it dispatched all carry the same ID, so "which command made this change" is answered by the ID. `--actor` is a value supplied by the operator, so it is not put into the user column of the data changes (the actual actor is the OS user) |
| `--actor=<email>` | Common to all audited commands. Records the responsible administrator account. An unknown email aborts the run |
| `--dry-run` | Prints the result without changing anything. Available on operations that are hard to undo |
| `--force` | Runs without confirmation prompts (for schedules and deployment scripts) |
| `--reason=` | Available on commands that require a reason |
| Exit codes | 0 success, 1 failure or cancelled, 2 a check command found a problem |
| DB context | While the command runs, the DB session actor is set to `system:command:{command}` and appears in the data changes (trigger) |

## Installation and demo

### `setup:install`

- Purpose: new installations and updates. Runs migrations, essential data, institution defaults, the installation profile and the initial administrator in turn. Safe to run again (existing data and values changed by administrators are kept).
- When: at first installation and on every deployment.
- Options: `--institution-name=`, `--locale=` (default language), `--timezone=` (for example `Asia/Seoul`), `--profile=*` (installation profile key), `--grade-scale=` (grade scale `4.5` or `4.3`. Cannot be changed once set. If empty, the scale of the first profile), `--admin-email=`, `--admin-name=`, `--force` (run without questions. The administrator password is read from standard input).
- Audit: recorded
- Examples

  ```bash
  php artisan setup:install
  echo "$ADMIN_PASSWORD" | php artisan setup:install --force --locale=ko --timezone=Asia/Seoul \
      --institution-name="Demo University" --admin-email=admin@example.ac.kr --admin-name="Administrator"
  ```

- Reading the output: `DONE`/`FAIL` per step. `Administrator exists` means a system administrator assignment already exists, so creation was skipped.
- On failure: if the error says a key is missing, put the values generated by `key:generate` and `pii:generate-key` into the environment configuration. A migration failure usually means the DB roles are not prepared (see the installation manual).

### `setup:demo`

- Purpose: creates data for a fictional university with factories. Prints the fixed demo accounts per role (`registrar@demo.test` and so on).
- When: development, training and demonstration environments. **It will not run in production (`APP_ENV=production`), even with `--force`.**
- Options: `--size=tiny|small|medium|large` (about 20/100/2,000/20,000 students. `tiny` is for tests and quick checks), `--seed=` (the same value produces the same data), `--force`.
- `--student-accounts`: creates an account for every active student (`student{student number}@demo.test`, the demo password) and writes them to `storage/app/private/load-accounts.csv`. For load tests ([Load testing](load-testing.md)).
- Audit: recorded
- Example: `php artisan setup:demo --size=small --seed=42`
- On failure: if the essential data is missing, the demo accounts have no roles and are skipped. Run `setup:install` first.

## Reference data and terms

### `reference:import`

- Purpose: imports reference data from CSV. Uses the same import rules as **Import CSV** in the administration panel (existing rows are matched by code and updated, empty translation cells keep the existing value, only failed rows are recorded separately).
- Arguments: `{type}` one of `org_units`, `programs`, `buildings`, `rooms`, `lookup_values`, `students`, `instructors`, `courses`, `registration_holds` / `{file}` a UTF-8 CSV with a header row.
- Options: `--actor=` (required. The import record and the completion notification go to this account), `--chunk=100` (rows per queue job), `--dry-run` (header check and row count only).
- Audit: recorded (type, file name, row count, failed row count)
- Column format: [Administrator manual chapter 9](../admin/09-csv-import.md).
- Exit codes: if the queue runs synchronously, the result is printed immediately and the exit code is 2 when there are failed rows. If asynchronous (Horizon), the import is only accepted and the exit code is 0. The result arrives as a failed-rows CSV in the administration panel notifications of the `--actor` account.
- Example: `php artisan reference:import org_units storage/app/org-units.csv --actor=admin@example.ac.kr --dry-run`

### `term:inspect`

- Purpose: shows the term in session at a given time and the open term windows (kind, term, target criteria, end time). Use it to check term and window configuration or to answer questions like "why is registration not open".
- Options: `--at=` (default now. For example `"2027-02-15 09:00"`. Without a time zone it is interpreted in the server time zone (UTC). A zone can be given as in `"2027-02-15 09:00 Asia/Seoul"`).
- Audit: not recorded
- Reading the output: date decisions use the institution time zone. Windows of terms in planned or archived status never open.

## Security

### `security:create-administrator`

- Purpose: creates an account with the system administrator role. Usually called by `setup:install`.
- Options: `--email=`, `--name=`, `--password-stdin` (password from standard input. Required for non-interactive runs).
- Audit: recorded (ID of the created user)
- Example: `php artisan security:create-administrator --email=admin@example.ac.kr --name="Administrator"`
- On failure: `system_administrator role is missing` means `setup:install` or `db:seed` must run first. The password must be at least 12 characters.

### `security:sync-permissions`

- Purpose: aligns the DB permission list with the permission catalog in code. New permissions are created; permissions missing from the catalog are deleted (and removed from every role). System roles always receive every permission.
- When: after deployment (`setup:install` does this as part of the essential data step).
- Options: `--dry-run` (prints only the create/delete list), `--force` (skips the deletion confirmation).
- Audit: recorded (permissions created/deleted)
- Reading the output: `create` and `delete` lines. A confirmation prompt appears when there are deletions.
- On failure: answering "no" to the confirmation exits with code 1 and changes nothing.

### `security:reset-mfa`

- Purpose: resets a user's two-factor authentication (authenticator app, email codes, recovery codes, remembered devices). The user enrolls again at the next sign-in. Use it when no administrator can sign in to the administration panel (for example the only administrator lost their phone). Otherwise use **Users > Reset two-factor authentication** in the administration panel.
- Arguments/options: `{user}` user email, `--reason=` (required), `--actor=` (required. The administrator who decided on the reset).
- Audit: recorded (both in the activity log and the security log, with the reason)
- Example: `php artisan security:reset-mfa admin@example.ac.kr --reason="Phone lost, identity verified by phone call" --actor=it-lead@example.ac.kr`

### `security:unlock-user`

- Purpose: unlocks an account locked by repeated wrong passwords before the lock period ends. Same as **Users > Unlock sign-in** in the administration panel.
- Arguments/options: `{user}` user email, `--reason=` (required).
- Audit: recorded (also in the security log)
- Reading the output: `The account is not locked.` means nothing was changed.
- Note: the lock thresholds (failed attempts, lock duration) are set under **Settings > Sign-in methods** in the administration panel.

## People and student records

### `people:find-duplicates`

- Purpose: lists people who appear to be the same person. The criteria are an identical national ID number (search hash), or an identical romanized name and date of birth. Merged people are excluded.
- Options: `--limit=100` (number of groups to print).
- Audit: not recorded (read only)
- Exit codes: 2 when duplicate candidates exist.
- Follow-up: review each group under **People** in the administration panel and, if they are the same person, run **Merge duplicate** from the page of the person to keep. A merge cannot be undone ([Administrator manual chapter 14](../admin/14-merge-and-invitations.md)).

## Admissions

### `admission:matriculate`

- Purpose: creates student records (new student numbers) for the enrollment-confirmed applicants of an admission cycle. Same as the bulk **Create student record** action under **Admissions > Applications** in the administration panel. Each applicant is processed separately, so one failure does not stop the others.
- Arguments/options: `{cycle}` admission cycle code, `--term=` (required. Admission term code, for example `2027-SP`. The admission date is the first day of the term), `--actor=` (required. An account with the `Create student records for admitted applicants` permission. Only applicants within that account's permission scope are processed), `--dry-run` (target list only).
- Audit: recorded (cycle, term, number of targets, number created, failed application numbers). An activity record (`application.matriculated`) is also written per applicant.
- Exit codes: 2 when any applicant failed.
- Example: `php artisan admission:matriculate DEMO-2027-REG --term=2027-SP --actor=admissions@example.ac.kr --dry-run`
- On failure: `not ready` means a student record already exists or the applicant is not in enrollment-confirmed status; `program is not in effect` means the program is not in effect on the admission date (check the effective period under Reference data > Programs).

### `admission:expire-drafts`

- Purpose: marks as **Expired** the draft applications of closed cycles and draft applications untouched for the configured period (**Settings > Admissions > Expire untouched drafts after (days)**, default 90 days). Expired applications do not block a new application in the same cycle.
- When: scheduled (daily at 03:10, [Scheduled jobs](scheduled-jobs.md)).
- Options: `--dry-run` (count only).
- Audit: recorded (number expired)

## Course sections

### `section:copy`

- Purpose: starts the planning of a new term from the sections of a previous term. Same as **Sections > Copy from another term** in the administration panel. Copies the sections that were not cancelled as drafts, together with the instructors (if still employed), meeting times and rooms, seat allocations (release times shifted by the difference between term start dates) and the syllabus (as a private draft). The course version is replaced by the version in effect at the start of the new session.
- Arguments/options: `{from-term}`, `{to-term}` term codes (for example `2026-FA`), `--org-unit=*` (only sections of this org unit code), `--dry-run` (results only, nothing saved), `--actor=` (required. Only sections within that account's `Plan sections` permission scope are copied).
- Audit: recorded (copied, skipped and needs-review counts)
- Reading the output: `skipped` means the target term already has the same section code or there is no course version in effect; `note` means the section was copied but something was left out (copied without a room because the room is already taken, a retired instructor, and so on). Sessions are matched by code; if there is none, the section goes into the full-term session.
- Example: `php artisan section:copy 2026-FA 2027-FA --actor=academic@example.ac.kr --dry-run`

### `schedule:check-conflicts`

- Purpose: checks the sections of a term before publishing the timetable. Double booking of rooms and instructors is already prevented by the DB; this finds the problems the DB allows: capacity above the room capacity, a course version not in effect at the session start date, a retired instructor, seat allocations above capacity, meeting dates outside the session. It also checks room conflicts in data that came in without constraints, such as a backup restore.
- Arguments: `{term}` term code.
- Audit: not recorded (read only)
- Exit codes: 2 when problems exist. Sections that have no instructor or room yet are shown for information only.

## Registration

### `registration:preflight`

- Purpose: checks a term before opening registration. Shows the registration and add/drop windows, the rule set, the number of published sections, sections with capacity 0, seat allocations above capacity, course versions not in effect at the session start date, the number of active students not covered by a credit limit, and the number of students with a registration hold.
- Arguments: `{term}` term code (for example `2027-SP`).
- Audit: not recorded (read only)
- Exit codes: 2 when problems exist. A missing rule set is shown for information, not as a problem (rule defaults apply).
- Example: `php artisan registration:preflight 2027-SP`

### `registration:simulate`

- Purpose: shows, rule by rule, what would happen if the student registered for the section now (or at a given time). Nothing is saved and no attempt is recorded. Use it for "why can I not register?" questions.
- Arguments: `{student-number}` student number, `{section}` `course code-section code` (for example `CSE2010-01`).
- Options: `--term=` (term code. Default is the most recent term that has that section), `--at=` (time of evaluation. For example `"2027-02-10 10:00 Asia/Seoul"`).
- Audit: not recorded (read only)
- Reading the output: per rule, pass/fail, block/warn and the message. A rule covered by an override shows as failed but does not block. Capacity is shown separately below the rule table.
- Exit codes: 2 when the registration would be refused.

### `waitlist:promote`

- Purpose: registers waitlisted students in order for sections that have free seats. Every rule is checked again at promotion; waitlist entries that fail a rule are removed from the waitlist (with the reason recorded). Waitlists of sections whose registration and add/drop windows are both closed expire. Students receive the result by email.
- Arguments/options: `{term?}` term code (default: every term with waitlist entries), `--actor=`.
- Audit: recorded (sections, promoted, removed, expired counts)
- When: on a drop, a withdrawal or a seat allocation release, the affected section is processed immediately by a queue job. This command is the hourly scheduled safety net that handles anything that was missed.
- Example: `php artisan waitlist:promote 2027-SP --actor=registrar@example.ac.kr`

### `registration:release-reserved-seats`

- Purpose: marks seat allocations whose release time has passed (for example seats reserved for majors) as processed and queues the waitlist promotion job for those sections. Reserved seats become general seats in the calculation as soon as the release time passes, so this command only hands the seats over to the waitlist.
- Audit: not recorded (runs every 5 minutes. Promotion results are in the registration records)
- When: scheduled (every 5 minutes).

## Grades

### `term:close`

- Purpose: closes a term. Every grade in the term must be finalized. For each student it calculates the term record (credits, term and cumulative GPA), determines the academic standing (good standing, academic probation, dismissal review) and honors eligibility (queue batch), then ranks honors per program, closes the term records as official records and sets the term to **Grades closed**. Same as **Grades > Term records > Close term** in the administration panel.
- Arguments/options: `{term}` term code, `--dry-run` (only checks whether the term can be closed), `--reason=` (reason kept in the record), `--actor=`.
- Audit: recorded (number of students, number of sections with unfinalized grades). When the close finishes, the `term.closed` audit record holds the counts of academic probation, dismissal review and honors.
- Exit codes: 2 when some sections have unfinalized grades (the unfinalized count per section is printed). 1 when the term is not in published status.
- When: after grade entry and finalization are complete. Follow batch progress in Horizon. Without a queue worker the term status does not change.
- Examples: `php artisan term:close 2026-FA --dry-run`, `php artisan term:close 2026-FA --reason="Fall 2026 grades closed" --actor=registrar@example.ac.kr`

### `grades:recalculate`

- Purpose: recalculates term records (credits, term and cumulative GPA) from finalized grades. Use it to apply a changed grading policy (GPA decimal places, retake handling) to past terms. Academic standing and honors keep the values decided at term close. An approved grade correction recalculates that student automatically, so this command is not needed for it.
- Options: `--term=` (students with grades in that term, from that term onwards), `--student-number=` (one student), `--reason=` (required), `--actor=`.
- Audit: recorded (number of students, reason)
- Example: `php artisan grades:recalculate --term=2026-SP --reason="GPA changed to three decimal places"`

### `grades:remind-missing`

- Purpose: emails the instructors of sections whose grades have not been submitted yet (not entered or saved as draft). Sections are grouped per instructor into one message each.
- Arguments/options: `{term}` term code, `--dry-run` (prints the targets without sending), `--actor=`.
- Audit: recorded (sections, instructors, messages sent)
- When: a few days before the grade entry window closes. Add it to the schedule if needed.

## Course evaluation

### `evaluation:remind`

- Purpose: emails students who still have unevaluated courses while the course evaluation window is open. The remaining courses are grouped per student into one message.
- Arguments/options: `{term}` term code, `--dry-run` (number of target students only, nothing sent), `--actor=`.
- Audit: recorded (target students, messages sent)
- When: once or twice during the evaluation window. Add it to the schedule if needed.

### `evaluation:publish-results`

- Purpose: publishes the term's course evaluation results to instructors. Same as **Course evaluation > Term evaluations > Publish results** in the administration panel. Even after publication, results are visible only for sections that reached the minimum number of responses and the response rate.
- Arguments/options: `{term}` term code, `--actor=`.
- Audit: recorded (number of responses, whether already published)
- When: after the evaluation window and grade processing are complete. A term already published is not changed.

## Certificates

### `certificate:verify`

- Purpose: checks a certificate verification code with the same criteria as the public verification page. Prints the kind, issue number, issue date and the masked holder.
- Arguments/options: `{code}` verification code.
- Audit: none (read only)
- Exit codes: 0 when valid, 2 for an unknown code, a revoked certificate or an expired validity period.

### `certificate:render`

- Purpose: renders the PDF of an issued certificate again with the current data and template, replacing the archived file. Same as **Issued certificates > Render again** in the administration panel. The issue number and verification code stay the same; the checksum changes.
- Arguments/options: `{issue}` issue number, `--reason=` (required), `--actor=`.
- Audit: recorded (issue number, new checksum)
- When: to regenerate a specific certificate after fixing a template or a name spelling.

## Examinations

### `assessment:import-results`

- Purpose: enters the results of an examination session from CSV. Same rules as **Examination sessions > Import results (CSV)** in the administration panel (registered students only, pass/fail decided from the score, entering again before publication replaces the results).
- Arguments/options: `{type}` examination kind code / `{held_date}` examination date `YYYY-MM-DD` / `{file}` a UTF-8 CSV with a header row, `--actor=` (required), `--dry-run` (row validation only, nothing recorded).
- Column format: [Administrator manual chapter 24](../admin/24-assessments.md).
- Audit: recorded (session, file name, row count, entered/absent/error counts)
- Exit codes: 2 when there are error rows (the other rows are recorded).
- Example: `php artisan assessment:import-results ENG_COMP 2026-05-15 storage/app/eng.csv --actor=registrar@example.ac.kr --dry-run`

### `assessment:publish-results`

- Purpose: publishes a session's results to students. Same as **Examination sessions > Publish results** in the administration panel.
- Arguments/options: `{type}` examination kind code / `{held_date}` examination date, `--actor=` (required).
- Audit: recorded (session, number of results)
- When: after result entry is complete. A session already published fails.

## Attendance

### `attendance:generate-sessions`

- Purpose: creates class meetings for every section of a term from its meeting times (weekday, time, period). Same as **Generate meetings** in the instructor portal and the administration panel. Existing meetings and their attendance are kept (safe to run again).
- Arguments/options: `{term}` term code, `--section=` (course code-section code, for example `CSE2010-01`, one only), `--dry-run` (number of target sections only), `--actor=`.
- Audit: recorded (term, sections, meetings created)
- When: before the term starts, after meeting times are confirmed. Run again when meeting times change.

## Graduation

### `degree-audit:run`

- Purpose: saves a graduation requirement audit for every active student. Same as **Degree audits > Run audits** in the administration panel. The latest saved audit is the basis for graduation processing.
- Options: `--term=` (term code the audit belongs to), `--student-number=` (one student), `--min-year-level=` (only this year level and above), `--actor=`.
- Audit: recorded (number of students, number satisfied)
- When: before graduation review (end of term), and after changing requirement sets or equivalent courses.

## LMS integration

### `lms:sync`

- Purpose: pushes published sections to the platform (course creation and linking, instructors, enrolled students). Does for a whole term what **Course links > Synchronize again** does in the administration panel. Sections already linked are only re-ensured (idempotent).
- Arguments/options: `{platform}` platform code, `--term=` (term code, default every term that has not ended), `--section=` (one course code-section code), `--dry-run` (only records what would be sent as "skipped"), `--actor=`.
- Audit: recorded (platform, sections, members, failures)
- Exit codes: 2 when any section failed.

### `lms:reconcile`

- Purpose: compares the platform's course rosters with the enrollment lists in the student information system, adds missing members and removes extra ones. Differences are kept in the sync log (`reconcile`).
- Arguments/options: `{platform?}` (every active platform if omitted), `--term=`, `--dry-run` (records differences only), `--actor=`.
- Audit: recorded (sections per platform, added/removed/failed counts)
- When: scheduled daily at 02:30. Run manually after a platform outage.

## Operational checks and cleanup

### `system:health-check`

- Purpose: checks configuration and keys (APP_KEY, PII keys, APP_DEBUG), the DB connection and roles (runtime, migrator, reporting), RLS on personal data tables, pending migrations, permission catalog sync, Redis, the queue (Horizon), Gotenberg, media storage writes and the scheduler heartbeat.
- Options: `--json` (output for monitoring).
- Audit: none (read only)
- Exit codes: 2 when any check fails.
- When: right after deployment, when an outage is suspected, periodically from monitoring.

### `audit:seal`

- Purpose: links new rows of the audit tables into the hash chain ([Audit integrity](audit-and-maintenance.md)).
- Options: `--table=` (one of record_changes, activity_log, security_events; repeatable), `--actor=`.
- Audit: recorded (rows sealed per table)
- When: scheduled daily at 03:30.

### `audit:verify-chain`

- Purpose: recomputes the content hashes and the chain of the audit rows to find tampering, deletions and reordering.
- Options: `--table=`.
- Audit: none (read only)
- Exit codes: 2 when there is a mismatch.
- When: before backups, during security reviews, after pruning.

### `audit:prune`

- Purpose: deletes **sealed** audit rows past their retention period. Runs on the schema owner connection.
- Options: `--before=YYYY-MM-DD` (required), `--table=`, `--dry-run` (counts only), `--actor=`.
- Audit: recorded (cutoff date, rows deleted per table)
- When: according to the retention policy, after a backup.

### `media:prune-orphans`

- Purpose: deletes media rows whose owner no longer exists and directories without a row (person photos, application documents, certificate PDFs, examination evidence).
- Options: `--dry-run` (list only), `--actor=`.
- Audit: recorded (rows, directories)
- When: monthly or after a bulk deletion.

## Personal data encryption keys

### `pii:generate-key`

- Purpose: prints new keys for `PII_ENCRYPTION_KEY` and `PII_HASH_KEY`. Saves nothing.
- Audit: not recorded
- Caution: changing `PII_HASH_KEY` invalidates every search hash. The key rotation procedure is in [security-keys.md](security-keys.md).

### `pii:reencrypt`

- Purpose: after a key rotation, re-encrypts personal data encrypted with a previous key using the current key. Runs as a queue batch.
- Arguments: the model class (currently `App\\Models\\Person\\Person`).
- Options: `--chunk=500`, `--dry-run` (only counts records using a previous key), `--force`.
- Audit: recorded (batch ID, number of jobs / preview count)
- Verification: follow the batch progress in Horizon (`/horizon`). When it finishes and `--dry-run` reports 0, remove the previous key from `PII_PREVIOUS_KEYS`.

## Localization

### `i18n:missing`

- Purpose: shows, per language, the keys missing compared with the base language (en) and the keys no longer used.
- Arguments/options: `{locale?}` (one language only), `--strict` (exit code 2 when keys are missing. Used in CI).
- Audit: not recorded

### `i18n:export`

- Purpose: creates a JSON file to hand to translators. Format: `{"key": {"source": "English text", "translation": "translation"}}`.
- Arguments/options: `{locale} {path}`, `--missing` (missing keys only).
- Audit: not recorded
- Example: `php artisan i18n:export ko storage/app/ko.json --missing`

### `i18n:import`

- Purpose: applies the JSON filled in by translators to `lang/{locale}`. Only keys that exist in the base language are imported; empty translations are ignored.
- Arguments/options: `{locale} {path}`, `--dry-run` (prints only the list of keys that would be written).
- Audit: recorded
- Caution: translation files are managed in the repository. Commit the changes after importing.

## Checks

### `naming:check`

- Purpose: checks the table and column names in migrations against the [naming conventions](../../../development/naming.md).
- Options: `--path=*` (directories to check, default `database/migrations`).
- Audit: not recorded
- Exit codes: 2 when problems exist.

### `pdf:sample`

- Purpose: renders a table mixing Korean, Chinese, Lao and English to PDF to check the fonts and the connection to the PDF service (Gotenberg).
- Arguments: `{path=pdf-sample.pdf}` (relative to the local disk `storage/app/private`).
- Audit: not recorded
- On failure: for a connection error, check `GOTENBERG_URL` and the state of the Gotenberg container.
