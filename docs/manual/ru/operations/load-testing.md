# Нагрузочное тестирование (пик записи на дисциплины)

С помощью k6 воспроизводится ситуация, когда множество студентов одновременно устремляются в одни и те же группы, как в первое утро записи на дисциплины. Сценарий — `tests/load/registration.js`.

## Подготовка

1. Сформируйте большой набор демонстрационных данных и подключите учётные записи студентов (CSV со списком учётных записей записывается в `storage/app/private/load-accounts.csv`).

   ```bash
   ./vendor/bin/sail artisan setup:demo --size=large --seed=42 --student-accounts
   ```

2. Период записи на дисциплины должен быть открыт (демонстрационные данные открывают период записи учебного периода текущего семестра).
3. Обработчик очереди (Horizon) и Redis должны быть запущены. Резервирование мест и продвижение листа ожидания выполняются через очередь.

## Запуск

```bash
docker run --rm -i --network ninefruits-laravel_sail -v "$PWD":/work -w /work grafana/k6 run \
    --vus 200 --duration 2m -e BASE_URL=http://laravel.test -e ACCOUNTS=/work/storage/app/private/load-accounts.csv tests/load/registration.js
```

- Повышайте `--vus` со 100 до 200 и до 500, наблюдая за p95 `http_req_duration` и долей ошибок. Целевые значения: p95 экрана записи < 800 мс, p95 запроса записи < 1,5 с, доля ошибок < 1 %.
- На стороне сервера также следите за числом ожидающих (на блокировках) сессий в `pg_stat_activity`, задержкой обработки в Horizon и насыщением обработчиков php-fpm.
- При запуске на Sail увеличьте число обработчиков встроенного сервера (`PHP_CLI_SERVER_WORKERS` в `.env`, по умолчанию 4). Число обработчиков ограничивает пропускную способность.

## Что гарантирует архитектура

- Вместимость защищена построчными блокировками БД (`SeatAllocator::lock`), поэтому даже поток одновременных запросов не может переполнить группу (`ConcurrentRegistrationTest`).
- Резервирование мест корректно работает только на уровне БД, без Redis и очереди, но продвижение листа ожидания и уведомления обрабатываются очередью.

## Решение об Octane

Если p95 превышает целевые значения на одном php-fpm под Sail, сначала настройте число обработчиков php-fpm и `max_connections` PostgreSQL или PgBouncer. Если этого всё ещё недостаточно, рассмотрите Laravel Octane (FrankenPHP или Swoole). Перед переходом на Octane проверьте: состояние, которое нужно сбрасывать для каждого запроса (сессионные переменные `DatabaseSessionContext` возвращаются в исходное состояние вызовом `reset()` в конце запроса, поэтому они безопасны и под Octane), пользовательские данные, остающиеся в синглтонах, статические кеши. Решение фиксируется в отчёте по этапу 13 после анализа реальных показателей нагрузки.

## Результаты от 2026-10-23

Контейнер Sail для разработки (встроенный сервер, без opcache), 100 VU в течение одной минуты: 24,7 запроса/с при 4 обработчиках, 34,5 запроса/с при 16 обработчиках, 0 ошибок HTTP, 0 переполнений групп, 4 подключения PostgreSQL. Серверное время на запрос — около 120 мс для страницы и 190 мс для записи; задержка в несколько секунд при 100 VU — это ожидание в очереди к обработчикам. Пропускная способность растёт с числом обработчиков PHP, а база данных далека от своего предела, поэтому **Octane не используется**: достаточно числа обработчиков php-fpm и горизонтального масштабирования серверов приложения. Перед вводом в эксплуатацию повторите прогон с 200 и 500 VU в промежуточной среде с php-fpm + opcache. Полные данные: [отчёт по этапу 13](../../../../porting/phase-13-report.md), раздел 7.
